# ChipFlow 项目面试拷打 100 问

本文档基于当前 **v0.2.0** 代码，而不是只基于 PRD。每题第一段给出可以直接用于面试的核心回答，第二段继续展开实现、取舍、风险或后续方案。回答时要主动区分“已经实现”“只具备接口骨架”和“下一阶段规划”，避免把原型包装成生产级平台。

## 一、产品定位与需求（1～10）

### 1. 这个项目解决的核心问题是什么？

芯片设计资料多、上下文长、角色协作复杂，设计人员需要在 FS、AS、ICD、DS、RTL 和工具日志之间反复追踪。ChipFlow 用角色型 Agent 理解和评审工程语义，用 Tool 执行确定性动作，并通过候选版本、Diff 和人工审批保留工程师控制权。当前真实闭环覆盖普通聊天、DS、RTL 候选和 Verilator Lint。

更具体地说，项目同时解决“知识理解”和“工程执行”两类问题：前者要求区分规格事实、推断和建议，后者要求执行结果可重复、可审计、可恢复。它不以替代工程师为目标，而是减少文档消化、方案初稿、错误归类和重复操作的时间。面试时可以强调，真正的价值不是生成一段文字，而是把模型输出接入权限、状态、证据和审批协议。

### 2. 为什么它不是一个普通的代码生成 Chatbot？

普通 Chatbot 主要返回文本，ChipFlow 还维护任务状态、来源、角色边界、Workspace、Patch、ToolRun、Issue Queue 和用户决策。模型不能直接覆盖 RTL；工具执行也必须经过权限和授权检查。

例如生成 RTL 时，LLM 只负责给出候选源码，`RTLService` 将其交给 `PatchService` 生成统一 Diff；用户批准前目标文件不发生变化。执行 Lint 时，也不是让模型拼一条 Shell 命令，而是调用预注册 Tool，由后端校验角色、路径、参数和批准位。因此系统输出不只是一段自然语言，还包括可以查询的 Task、Run、Issue 和 Patch 状态。

### 3. 目标用户是谁？

当前主要面向 RTL 设计和验证工程师。设计人员关注 DS、RTL、Lint 和后续综合时序；验证人员关注已有用例执行、仿真日志和问题归因。真实架构师目前通过用户反馈和问题单结论参与，而不是直接作为系统用户。

不同用户的默认工作方式不同：设计人员通常已有验证团队提供的用例，只需在约定目录发现并执行；验证人员可能需要分析失败来自 RTL、Testbench、激励还是期望值。系统中的虚拟 Architecture Agent 不是组织中的批准人，只提供架构视角。当前没有登录与用户画像，因此这些差异主要通过请求中的角色和显式操作表达。

### 4. 为什么不让系统自动决定进入哪个研发阶段？

芯片项目阶段受组织流程、依赖成熟度和风险接受度影响，不能仅由模型根据文档推断。系统只响应用户明确目标，例如“生成 DS”或“执行 Lint”，Orchestrator 负责组织角色和 Tool，不替用户宣布阶段完成。

如果系统自动推进阶段，很可能把“生成了候选 DS”误判为“DS 已批准”，或把“一次 Lint 通过”误判为“RTL 可以 Sign-off”。产品因此区分任务完成和项目阶段完成：前者由系统状态表示，后者仍由用户和真实流程决定。当前自然语言路由主要覆盖 Chat/DS，RTL 与 ToolRun 还需要用户从工程工作台显式发起。

### 5. 为什么 FS、AS、ICD 被视为只读资料？

它们是架构基线，错误修改会影响大量下游设计。虚拟 Architecture Agent 只能解释、质疑和提出建议；正式修改需要真实架构结论、问题单或新版文档。当前代码没有原始规格回写接口。

这种约束也为未来的记忆失效传播提供基础：任何从规格形成的 Reflection 都应保存来源和版本，规格变更后才能定位受影响的 DS、RTL 和验证结论。当前版本只保存部分来源信息，还没有完整依赖图，因此宁可不开放原始文档修改，也不制造无法追踪的隐式变更。

### 6. v0.1 和 v0.2 的区别是什么？

v0.1 聚焦聊天、文档上传、FS/AS 到 DS、多角色评审和人工冲突恢复。v0.2 新增 SQLite 快照、Workspace、Artifact、RTL Candidate、Patch Review、Tool Registry、异步 ToolRun、日志解析和逐条 Issue 交互。

架构上的关键变化，是系统从“模型工作流”扩展为“工程状态机”。v0.1 的主要状态位于 LangGraph 和前端；v0.2 开始把 Workspace、Patch、Run、Issue、用户决策落到 SQLite 和文件系统。需要说明的是，v0.2 仍是第二阶段骨架：真正接入的 EDA Tool 只有 Verilator Lint，自动修复与复验尚未完成。

### 7. 当前产品最有价值的设计是什么？

不是“模型会写 RTL”，而是把不确定的模型输出放进受控工程协议：模型生成候选，系统生成 Diff，用户审批，写入时再次检查目标是否变化。这个协议可以复用于 DS、RTL、Testbench 和约束修改。

该协议同时解决三个风险：模型可能理解错规格、用户可能在 Review 期间修改目标、写文件中途可能失败。对应措施分别是人工 Review、before-content 乐观并发校验和临时文件原子替换。它比单纯提升 Prompt 更具有通用工程价值，因为即使更换模型，安全边界仍然成立。

### 8. 当前最明显的产品缺口是什么？

商业 Sim、CDC、综合和 STA 尚未接入；工具 Issue 还没有自动生成修复 Patch并执行最小复验；长期记忆、问题单、Git、多用户权限也未完成。

其中最值得优先补齐的是一条真实的闭环，而不是一次增加很多空接口：用实际错误 RTL 跑 Verilator，分析首错，生成候选 Patch，用户批准，重新 Lint，并根据结果进入 resolved 或 reopened。完成这条链路后，再复制 Adapter 模式到 Sim、CDC 和综合会更可靠。

### 9. 为什么第一版优先支持 SystemVerilog？

当前目标是 RTL 设计工作流，SystemVerilog 能表达现代组合/时序风格、类型和断言。缩小语言范围有利于建立可检查的生成规范。Verilog-2001 可以作为兼容输入，但不应在首版扩大生成和验证矩阵。

SystemVerilog 也便于在生成规范中明确 `always_ff`、`always_comb`、复位值和类型转换等规则。支持更多语言不仅是修改文件后缀，还涉及解析、Lint 参数、代码模板和测试矩阵，因此应根据真实项目需求逐步扩展。

### 10. 如何衡量这个产品是否真正有用？

应关注需求到设计追踪完整率、问题发现提前量、Diff 接受率、工具首错定位准确率、平均问题处理时间、回归通过率和工程师节省时间，而不是只看模型回答满意度。

可以把指标分为三层：模型层看 JSON 成功率和引用准确率；工程层看 Patch 接受率、复验通过率和错误归因准确率；业务层看 DS/RTL 周期和缺陷逃逸率。为了避免指标失真，还应记录用户跳过建议的原因及最终人工结论。当前代码尚未实现完整指标系统。

## 二、Multi-Agent 与角色设计（11～25）

### 11. 这个系统真的算 Multi-Agent 吗？

它是逻辑角色型 Multi-Agent：不同角色有独立职责、提示词、权限和工作流节点，但目前共享模型配置，也不是独立进程。这里的 Multi-Agent 强调职责隔离和协作协议，而非部署数量。

从代码看，角色目录位于 `app/agents/definitions.py`，真实行为由 Runtime 方法和 LangGraph 节点承载。面试时不要把多个 Prompt 等同于完全自治的 Agent 社会；当前更准确的说法是“一个模型运行时承载多个有边界的 Agent 角色”。未来可以为不同角色选择不同模型，但领域协议不需要随之改变。

### 12. 为什么按生产角色设计 Agent，而不是每个任务一个 Agent？

真实组织中的责任边界相对稳定，而单项任务数量会持续增加。如果每个命令都建 Agent，会产生大量重叠提示词和权限。项目把架构、设计、验证、评审设为 Agent，把读文件、跑 Lint、解析日志等动作设为 Tool。

这种划分也更容易测试：角色判断用场景和结构化输出评估，Tool 用确定输入输出做单元测试。新增一个综合报告解析器通常不需要新增“综合 Agent”，而是让 Design Agent 调用综合 Tool，再由专项 Reviewer 检查结果。

### 13. Agent 和 Tool 的本质区别是什么？

Agent 负责语义理解、方案权衡、根因判断和自然语言解释；Tool 负责输入输出明确、可校验、可审计的确定性动作。Tool 不应隐藏设计决策，Agent 不应绕过 Tool 直接执行危险操作。

例如“这个 WIDTH 错误是否会造成功能截断”属于 Agent 判断，“读取报错行、运行 Verilator、保存日志”属于 Tool。这个边界保证同一 Tool 可以被不同角色复用，也保证真正的文件和进程权限由后端代码控制，而不是由模型自报权限。

### 14. Orchestrator Agent 做什么？

设计目标是根据用户明确目标选择角色、评审视角和 Tool，并维护执行计划。当前代码已经定义该角色，但通用动态编排尚未完全接入；DS 仍主要由固定 LangGraph 编排，RTL/ToolRun 由工程工作台显式调用。

完整实现时，Orchestrator 应输出结构化计划，例如目标、前置条件、角色、Tool、批准点和失败恢复策略，而不是自由文本。它还应读取 Tool Registry 元数据做权限过滤。当前不能声称已经实现 LLM 原生 Function Calling 编排，这一点在面试中应主动说明。

### 15. Conversation Router 和 Orchestrator 有什么区别？

Router 只做轻量意图分类，目前主要判断普通聊天或 DS 工作流。Orchestrator 的范围更大，应拆解工程目标、选择角色和 Tool、处理依赖与重试。当前 Router 已实际使用，完整 Orchestrator 仍是演进项。

将两者分开可以降低普通聊天的开销：每次用户问一个概念都不需要生成复杂执行计划。只有检测到工程目标后才需要 Orchestrator。当前 Router 的输出只有 route 和 reason，便于前端展示为何进入某条路径。

### 16. Architecture Agent 为什么没有修改 FS/AS 的权限？

虚拟 Agent 不具备组织授权，也无法确认所有上下游影响。它的结论是建议而非正式架构决策。即使其置信度很高，也必须由真实架构师或受控问题单支撑后才能改变基线。

这不是模型能力问题，而是治理问题。真实生产中，接口变更可能影响其他模块、验证环境、软件和项目进度，局部上下文无法代表完整影响范围。因此系统采用“发现问题—内部讨论—升级用户—带回问题单证据”的流程。

### 17. Design Agent 当前做了什么？

它参与 AS 子模块识别、DS 生成、RTL Candidate 生成，并作为 Verilator Tool 的允许调用角色。当前并没有完成基于工具 Issue 的自动 RTL 修复闭环。

Design Agent 的写权限也不是直接文件权限：它只能产生候选内容，真正创建和应用 Patch 由 Service 完成。这样即使 Prompt 被污染，模型也无法绕过审批写正式文件。后续修复闭环仍应沿用同一模式。

### 18. Verification Agent 为什么不默认制定验证计划？

产品假设验证计划通常由真实验证团队负责。对设计人员，Verification Agent 主要检查可验证性、发现已有用例并执行验证侧 Tool；只有用户明确提出验证资产任务时，才应生成候选 Testbench 或用例。

这个设计避免系统替验证团队重复或篡改既有计划。`discover_testcases` 只扫描约定目录，不创建内容。未来 Verification Agent 生成 Testbench 时也应先生成候选 Patch，并限制在验证目录和对应权限内。

### 19. 为什么评审 Agent 要与生产 Agent 分开？

生成者容易为自己的方案寻找合理化解释。独立 Reviewer 使用不同检查目标，可以减少自我批准和虚假共识。当前有规格一致性、微架构、可验证性和接口一致性四个默认 Reviewer。

Reviewer 只返回 Finding，不直接批准或修改。其输出仍然是模型建议，因此用户可以结合严重度和来源决定是否处理。后续可以把生产 Agent 和 Reviewer 分配给不同模型或不同上下文，进一步降低相关性偏差。

### 20. Specialist Reviewer 是什么？

它用于按任务加载 CDC、低功耗、安全、DFT、PPA 或时序专项清单。当前只完成角色元数据，还没有自动识别模块特性并加入工作流，因此不能声称这些专项评审已经落地。

合理的触发方式应结合文档标签、时钟/电源域信息、工具结果和用户指令，而不是只靠关键词。Orchestrator 还要说明为何选择某专项评审，避免无关角色带来额外成本和噪声。

### 21. 多 Agent 如何共享上下文？

DS 工作流通过统一 State 共享请求、文档、分析结果、Issue、用户结论和 DS。每个角色只读取所需字段并写入自己的结果。当前没有独立 Agent 私有长期记忆或消息总线。

统一 State 的优点是数据流清晰、可测试，缺点是字段增多后容易形成大对象。演进时可以用 Artifact ID 和 SourceRef 替代重复大文本，并通过共享存储传递制品，而不是让所有 Agent 复制完整上下文。

### 22. 如何防止 Agent 形成虚假共识？

提示词要求 Reviewer 独立输出，规格证据优先于 Agent 推断；未解决的冲突达到轮次上限后必须升级用户。更完整的方案还应保存反方意见、证据强度和被否决方案，当前只实现了基础版本。

真正防止虚假共识不能只依赖“请独立思考”的提示词，还需要协议约束：每个结论带来源、置信度和未解决项；没有新证据时不得改变立场；架构分歧不能由多数投票覆盖正式文档。当前实现主要具备轮次上限和人工升级。

### 23. 为什么内部讨论默认限制轮次？

无限讨论会增加 Token、延迟，并可能让模型为了结束而制造共识。当前允许 1～3 轮，默认 2 轮；没有新证据时升级用户，而不是继续消耗模型调用。

轮次上限是成本与可靠性的保护阀，而不是说两轮一定能解决问题。更好的停止条件应比较各轮是否出现新证据或新结论；当前讨论节点主要记录轮次，还没有进行真正多模型辩论，这也是明确的实现边界。

### 24. 用户能禁用 Agent 吗？

DS 请求支持 `disabled_agents`。工作流跳过对应角色，并在 `quality_warnings` 中记录质量下降，避免“跳过检查但仍宣称完整评审”。

禁用功能既满足用户控制，也有助于故障降级，例如某 Reviewer 持续输出错误时仍可交付候选。但核心写操作、路径保护和审批不能被 Agent 禁用，因为它们属于系统安全边界而非可选角色。

### 25. 自定义 Reviewer 如何实现？

用户可提交额外评审提示词，工作流以 `custom_reviewer_n` 调用通用 Review 接口并聚合 Finding。它提供扩展性，但生产环境还需要提示词审批和注入防护。

当前自定义 Reviewer 会收到 DS 和受控文档上下文，输出与默认 Reviewer 相同的 Finding 结构。为了生产化，还应限制提示词长度、记录创建者、保存版本，并防止自定义内容要求越权调用工具或泄露密钥。

## 三、总体架构与工作流（26～40）

### 26. 为什么选择 FastAPI？

它与 Pydantic 契约结合紧密，适合构建类型明确的本地 API，原生 OpenAPI 也方便前后端联调。异步接口能承载模型请求，但当前 EDA 工具采用后台线程而不是阻塞请求。

FastAPI 还便于把校验失败映射为 422，并通过依赖明确的 Response Model约束公开字段，例如模型设置永远不返回完整 Key。选择它并不是因为“AI 项目都用 Python”，而是模型 SDK、文档解析、LangGraph 和工程服务都处于同一 Python 生态，降低了跨语言集成成本。

### 27. 为什么选择 LangGraph？

DS 流程包含并行分析、条件分支、循环讨论、Interrupt 和 Resume，图模型比手写 if/else 更清楚。它也为未来 Checkpointer 和可观测性提供扩展点。

每个节点只处理一类职责，条件边明确表示无冲突、继续讨论、等待用户或取消。这样可以单独测试节点输入输出，也便于未来插入专项 Reviewer。代价是状态 Schema 和 Checkpointer需要认真设计；当前 MemorySaver 还不能满足生产恢复。

### 28. DS 工作流的完整路径是什么？

准备上下文后并行执行架构、设计、验证分析，汇合进行冲突检测；无冲突则生成 DS，有冲突则进入有限讨论并可能等待用户；DS 生成后并行执行四类默认评审和自定义评审，最后聚合 Finding 并交付。

状态从 requested 进入 executing，冲突时进入 internal_discussion 或 waiting_for_user，DS 生成时进入 reviewing，最终 delivered。用户取消则走独立 cancelled 分支。这个流程交付的是候选 DS 和 Finding，不代表真实评审会签完成。

### 29. 为什么三个分析节点并行？

它们都只依赖冻结的初始请求，彼此没有数据依赖。并行可降低总时延，并保持不同角色先独立判断再汇合。

如果先让 Design 读取 Architecture Agent 的结论，可能导致锚定偏差；先独立分析再汇合能保留不同视角。当前 LangGraph 图结构表达了这种扇出/汇合关系，但真实模型供应商是否真正并发还受执行器和连接限制影响。

### 30. 为什么冲突处理需要 Human-in-the-loop？

规格矛盾属于架构权责问题。模型可以识别和讨论，但没有权限创造正式结论。工作流通过 Interrupt 返回问题和允许动作，等待用户带回真实架构结论或接受临时假设。

Interrupt Payload 包含 Issue、提示信息和允许动作，前端据此显示真实架构反馈表单。用户反馈可以附问题单编号，后续 DS 会记录该证据。这样系统既能继续工作，又不会悄悄把临时假设伪装成架构事实。

### 31. 用户可以怎样处理规格问题？

可以提供正式结论及问题单引用、接受临时假设、忽略继续或取消任务。提供正式结论时必须有内容；系统会把反馈写入 DS 候选的假设与决策部分。

四种动作的风险不同：正式结论可信度最高；临时假设应保留风险；忽略意味着用户接受未解决项；取消则不生成 DS。当前状态模型没有对这些风险做更细粒度评分，后续应在交付报告中持续展示未关闭问题。

### 32. 为什么统一使用 Pydantic 领域模型？

它把 HTTP、Service 和前端需要的字段稳定下来，集中做枚举、必填项和范围校验，避免每层使用随意字典。当前前端类型仍手工同步，后续应从 OpenAPI 生成 Client。

例如 DS 请求通过 Validator 要求至少一份 AS，讨论轮次限制在 1～3；ToolRun 的角色和状态由枚举控制。领域模型还避免把数据库内部的 before/after 原文等敏感实现细节全部暴露给前端。

### 33. API 层为什么不直接写业务逻辑？

路由只负责参数、状态码和异常转换；Workspace、Patch、ToolRun 等逻辑放在 Service，才能进行独立单元测试，也避免未来 CLI 或任务队列重复实现业务规则。

例如 Patch 冲突在 Service 抛出 `ValueError`，HTTP 层转换为 409；同一个 PatchService 未来可以被 CLI 或 Orchestrator 调用。若把原子写入和并发校验直接写在路由中，就难以复用和测试。

### 34. 当前有多少 API？

OpenAPI 当前包含 22 个 Path，覆盖健康与诊断、模型设置、文档抽取、聊天与 DS、Workspace/Artifact、RTL/Patch、ToolRun 和 Issue 决策。

面试时比记数量更重要的是能按资源边界解释：Task 是模型工作流状态，Workspace/Artifact 是工程资产，Patch 是候选修改，ToolRun 是一次执行，EngineeringIssue 是执行结果的标准化问题。API 采用这些资源而不是按页面按钮随意设计。

### 35. 为什么文档上传不直接触发工作流？

上传只是增加上下文，不代表用户授权生成或修改工程资产。Router 只有检测到明确的 DS 交付动作才启动工作流，普通文档提问仍由 Chat Agent 回答。

这也避免用户刚上传敏感文档就触发多次付费模型调用。前端会让用户修正文档类型和版本，再通过自然语言明确任务。当前上传抽取文本主要保存在浏览器状态，尚未成为正式文档库资产。

### 36. 为什么没有把所有流程都塞进一个 LangGraph？

当前 DS 是成熟的图流程，而 RTL 和 ToolRun 更适合先通过独立 Service 和状态机落地。强行放入一个巨型图会增加耦合。后续 Orchestrator 可以组合子图，而不必让所有任务共享同一 State。

图适合表达推理依赖和人工暂停，ToolRun 更像有明确状态和外部进程的作业系统。将其分开还能独立扩展可靠队列和 Worker。未来可以由顶层 Orchestrator 启动 DS 子图、RTL Service 或 ToolRun，而不是把所有细节节点平铺在一张图里。

### 37. 事件列表有什么作用？

它让前端展示哪些角色完成了什么步骤，并保留基础审计线索。但当前事件缺少统一时间戳、耗时、Token 和 Actor 信息，还不是完整审计日志。

事件采用追加 reducer，避免并行节点互相覆盖。生产化时应为每个事件增加 event_id、task_id、timestamp、actor、input/output artifact、request_id、耗时和模型用量，并考虑不可变事件表而非只嵌在 Task 快照中。

### 38. 为什么使用统一异常响应？

用户此前只看到 `Internal Server Error`，无法定位。现在未知错误、模型调用和密钥解密错误都带错误码、请求编号和建议；前端可以把请求编号展示给用户用于日志关联。

统一中间件为请求生成或透传 `X-Request-ID`，异常处理器把它同时写入日志和响应。模型异常保留可理解原因，未知异常对用户隐藏堆栈，避免泄露内部路径或密钥，同时提示查看后端同编号日志。

### 39. 当前系统是同步还是异步？

模型和 DS 工作流通过异步 API 调用，但一次 DS 请求仍会等待工作流到交付或 Interrupt。ToolRun 采用异步提交：API 返回 202 和 Run ID，后台线程执行，前端轮询。

这是一种混合模型。DS 的模型调用可能较慢，未来可以也改成任务化和流式事件；ToolRun 已有独立生命周期，更适合轮询或 SSE/WebSocket。当前轮询简单可靠，但并发用户多时会增加请求负载。

### 40. 架构如何支持未来拆服务？

领域契约、Service、Tool Registry 和持久化已经分层，未来可以把 ToolRun 放入独立 Worker 或队列，把模型 Runtime 做成服务。但当前单机部署无需提前引入分布式复杂度。

拆分时应以资源所有权为界：API 只创建 Run，Worker 消费消息并写状态，Artifact 存储保存大日志，数据库维持事务状态。不能只按技术目录机械拆服务，否则会增加跨服务一致性问题。

## 四、模型接入与输出可靠性（41～50）

### 41. 当前支持哪些模型？

通过 OpenAI Python SDK 支持 OpenAI Responses、OpenAI 兼容 Chat Completions，以及 DeepSeek 对应接口。模型名和 Base URL 可配置，当前并不保证所有自定义兼容服务都完全兼容。

Provider 对 DeepSeek 的 system role 和最大 Token 参数做了适配，同一上层 Runtime 不感知协议细节。用户仍需要使用服务商实际存在的模型名；连接测试只能证明最小请求可用，不能证明所有结构化输出场景都可靠。

### 42. 模型配置在哪里？

默认配置在 `config/model.toml`，网页覆盖在 `data/model_settings.json`，环境变量优先级最高。前端可以配置 provider、API 风格、模型、Base URL、超时、输出 Token 和 API Key。

这种三级合并既提供可提交的安全默认值，也允许单机用户持久化选择，并让部署环境通过环境变量覆盖。DeepSeek 和 OpenAI 分别保存 Key，避免切换供应商时错误复用凭据。

### 43. API Key 如何保存？

Windows 下使用 DPAPI 加密并绑定当前 Windows 用户，后端查询只返回掩码。环境变量 Key 不写磁盘。它适合本地单用户，不等同于企业 Secret Manager。

保存时使用临时文件替换配置，减少写入中断导致 JSON 损坏。DPAPI 密文被复制到另一用户或机器后通常无法解密，此时系统自检会给出重新输入 Key 的建议。生产环境还需要密钥轮换和访问审计。

### 44. 为什么需要 Deterministic Runtime？

它让开发、测试和演示不依赖网络，不消耗模型费用，还能稳定验证工作流、权限和持久化。它只提供可预测模板，不能替代真实模型的开放式语义能力。

自动化测试在 `conftest.py` 强制关闭真实模型，因此 CI 结果不会受用户本地设置或模型波动影响。Deterministic Runtime 也用于验证 RTL 候选必经 Patch，而不是验证生成逻辑质量。

### 45. 系统如何选择真实模型或模拟运行时？

测试可通过 `CHIP_AGENT_MODEL_ENABLED=false` 强制模拟；否则有效配置同时满足 enabled 和可用 Key 时选择 LLM Runtime，条件不满足则回退 Deterministic Runtime。

Runtime 每次调用时读取有效设置，因此网页保存后无需重启后端。需要注意，自动回退有可用性优势，但也可能让用户误以为真实模型在工作，所以前端顶部明确显示“真实模型”或“模拟运行时”。

### 46. 如何处理模型返回非法 JSON？

Provider 会去除代码 Fence，并尝试从附加说明中提取 JSON；首次失败时发起一次仅修复格式的请求；仍失败则抛出包含具体 Agent 名称的 `ModelInvocationError`，不会把错误结果当作有效结论。

修复请求必须强调只修格式、不修改结论，否则第二次调用可能悄悄改变业务答案。即使解析成功，还要通过代码检查对象/数组结构和字段类型。对高风险结果，未来应使用供应商 Structured Outputs 或本地 Schema 校验。

### 47. 为什么不用原生 Structured Outputs？

项目需要兼容 DeepSeek 和不同 API 风格，首版采用提示词契约加 Python 校验。缺点是仍需修复和错误处理；未来供应商能力稳定后可按 Provider 使用 JSON Schema。

Structured Outputs 能降低格式失败，但不能解决语义错误、幻觉和权限问题。因此即使升级为严格 Schema，来源校验、人工审批和 Tool 权限仍然必要，不能把格式可靠性等同于工程正确性。

### 48. 如何控制超长文档？

真实 Runtime 当前按文档顺序裁剪总上下文，约 120,000 字符。它简单但可能丢失后部内容。更合理的方案是文档分块、SourceRef、检索和按任务选择章节。

未来应先按章节、表格和接口定义形成结构化 Chunk，再根据模块、问题和依赖检索；对关键 AS/ICD 条目可以提高优先级。还要把实际传入片段记录为证据，便于复现模型为什么得出某结论。

### 49. 如何防止模型幻觉？

提示词要求区分事实、推断和建议，DS/RTL 不得发明外部接口，不确定内容必须标记 TODO 或开放问题；架构冲突升级用户；修改还要经过 Diff Review。当前尚未实现完整的引用级自动事实校验。

防幻觉是多层防线：输入层提供受控文档，生成层限制角色，评审层独立检查，执行层使用 Tool 验证，写入层要求人工批准。任何单层都不能保证正确，尤其不能仅依赖“不要幻觉”提示词。

### 50. 如何控制模型成本？

当前通过按需路由、讨论轮次上限、确定性测试和上下文裁剪控制。尚未实现 Token 预算、缓存、角色模型分级和成本面板，这些是生产化必须补充的能力。

进一步可以给任务设置总预算，普通 Router 使用小模型，关键架构/评审使用强模型；相同文档摘要按版本缓存；超过预算时暂停并让用户选择继续。成本指标应与接受率和缺陷发现价值一起看，不能只追求最低 Token。

## 五、持久化、记忆与一致性（51～60）

### 51. 为什么选择 SQLite？

当前是 Windows 本地单机产品，SQLite 零部署、事务可靠、便于调试，足以保存 Workspace、Patch、ToolRun、Issue 和任务快照。多用户和多 Worker 时再迁移 PostgreSQL 更合理。

选择 SQLite 是阶段性权衡：它让 MVP 不依赖外部数据库，同时支持事务、唯一索引和外键，比散落 JSON 文件更可靠。代码将数据库访问集中在 `app/storage/database.py`，为未来替换存储层保留边界。不过当前 SQL 直接写在 Service 中，迁移 PostgreSQL 时仍需要 Repository 抽象和迁移工具。

### 52. SQLite 中有哪些表？

`workspaces`、`artifacts`、`patches`、`tool_runs`、`engineering_issues` 和 `task_snapshots`。数据库启用外键和 WAL。

这些表分别对应工程空间、版本化资产、候选修改、执行记录、标准化错误和 Agent 任务快照。Issue 对同一 Run 的 fingerprint 建唯一索引，Artifact 按 Workspace 和路径查询版本。当前没有用户、项目权限、模型调用审计和完整事件表。

### 53. TaskService 的内存状态和 SQLite 快照是什么关系？

内存字典保存当前进程的热状态，创建和恢复后同步写入 SQLite。查询时若内存不存在会加载 SQLite。这使已完成任务可查询，也支持等待任务的兼容恢复。

热状态保留 LangGraph 返回的 Interrupt 对象，而落库前会去除不可序列化对象并单独保存 Pending Payload。这样正常运行优先走原生 Resume，重启后才走兼容路径。两个状态源意味着必须保证每次状态变化都持久化，未来更理想的方案是以持久化 Checkpointer 为单一事实来源。

### 54. 是否已经实现持久化 LangGraph Checkpointer？

没有。图内部仍使用 `MemorySaver`。SQLite 保存的是应用层可序列化快照；后端重启后的恢复由 TaskService 根据快照重新生成 DS 和评审，不是精确从原图节点续跑。

这个区别影响幂等性和费用：兼容恢复可能再次调用生成和评审模型，而真正的 Checkpointer 应恢复到具体节点并保留已完成写入。面试时应明确说“业务可恢复”不等于“工作流精确恢复”。

### 55. ToolRun 在后端重启后能恢复吗？

已完成的 Run、日志和 Issue 可以查询；正在运行的外部进程不会被重新接管，状态也不会自动校正。这需要可靠队列、Worker 心跳和孤儿任务恢复策略。

生产方案可以给 Run 保存 worker_id、heartbeat、pid 或外部作业 ID；服务启动时扫描过期 running 状态，根据 Tool 幂等性决定重新排队、标记失败或要求人工确认。高成本综合/STA 不应无条件自动重跑。

### 56. Artifact 如何版本化？

同一 Workspace 和相对路径每次创建时版本号递增，并记录 SHA-256、类型、状态、来源和时间。当前没有内容寻址存储和 Artifact 间完整依赖图。

版本号便于用户理解，Hash 用于检测内容一致性和未来缓存。`derived_from` 目前只是字符串列表，还不能强制引用真实 Artifact ID 或自动做影响分析。下一步应建立规范化依赖边和 superseded 状态传播。

### 57. 当前实现长期记忆了吗？

没有。SQLite 中的是工程状态和任务快照，不等同于长期语义记忆。PRD 中的记忆形成、合并、反思、遗忘、检索和来源失效传播仍未实现。

长期记忆至少应区分不可改原始资料、带来源项目事实、临时假设、用户决策和通用经验；不同类型有不同生命周期和可信度。直接把对话向量化并不够，因为无法处理版本冲突、撤销和审计。

### 58. 为什么所有 Reflection 都应保存来源？

当 FS/AS 版本变化时，需要找到并失效所有基于旧内容的推论。没有来源边，就无法区分项目事实和模型推断，也不能做可靠影响分析。

理想数据结构应记录 `derived_from`、形成时间、形成 Agent、置信度、适用范围和状态。更新源文档时沿依赖图把结论标为 stale，重新评估后再恢复有效，而不是立即物理删除历史。

### 59. 如何处理两个版本的规格结论？

设计上应按受控文档版本和正式问题单决定有效结论，旧结论保留历史但标为 superseded，并传播影响。当前 Artifact 有版本和来源字段，但完整结论选择与失效传播尚未实现。

优先级不能简单按“最新时间”，还要考虑证据类型：新版受控文档或问题单结论高于口头转述，虚拟 Agent 推断不能覆盖文档事实。发生文档内部冲突时应进入讨论和真实架构升级流程。

### 60. SQLite 并发策略是什么？

Database 使用进程内 `RLock`、短连接、事务提交和 WAL，连接允许跨线程创建。它适合当前线程池规模，但不适合多进程高写并发；生产化应迁移数据库和迁移工具。

短连接减少跨线程复用连接的风险，WAL 改善读写并发。当前没有连接池和重试策略，长事务也没有专门控制。迁移多 Worker 前应增加 Repository、Alembic 和冲突重试测试。

## 六、RTL、Workspace 与 Patch（61～70）

### 61. RTL Candidate 的输入是什么？

项目、可选 Workspace、模块名、目标路径、已确认 DS、可选规格文档和用户指令。Design Runtime 返回 SystemVerilog 文本，RTLService 随后创建 Patch。

如果没有 Workspace，Service 会为项目创建隔离目录；默认目标为 `rtl/<module>.sv`。输入 DS 目前由前端当前 Task 提供，系统尚未强制它必须是已批准 Artifact，因此“已确认”主要依赖用户流程，后续应以 Artifact 状态校验。

### 62. 为什么 RTL 不能直接写文件？

LLM 输出存在理解错误、接口幻觉和代码质量风险。先生成 Patch 可以让用户查看精确变化，保存原因和来源，并防止模型绕过审批修改正式资产。

Patch 还为后续审计和自动复验提供锚点：系统可以知道哪些文件和行发生变化，从而选择最小工具集合。即使用户最终拒绝，候选和原因仍可保留用于比较，而不会污染正式文件。

### 63. PatchService 如何防止覆盖并发修改？

创建 Patch 时保存 before 内容；用户批准时再次读取目标，若当前内容与 before 不一致就返回 409，要求基于新版本重新生成 Patch。

这是乐观并发控制。它不锁住用户文件，适合人工 Review 时间不确定的场景；代价是冲突后需要重新生成。生产版可改用 Hash 而非保存全文比较，并提供三方合并预览，但不能静默覆盖。

### 64. 文件写入为什么使用临时文件替换？

直接写入中途失败可能留下半文件。WorkspaceService 先在同目录写临时文件，再执行原子 replace，降低进程异常造成文件损坏的风险。

临时文件与目标位于同一文件系统，能提高 replace 原子性的可靠度。数据库 Patch 状态在文件写入后更新；极端崩溃仍可能出现文件已写但状态未更新，因此更严格的实现需要恢复扫描或事务日志。

### 65. 如何防止路径穿越？

所有目标必须是相对路径，解析为绝对路径后验证其自身或父目录链位于 Workspace 根目录内。`../outside` 和绝对路径都会被拒绝。

只检查字符串前缀是不安全的，因为相似目录名和规范化路径可能绕过；代码使用 `Path.resolve()` 后检查父目录关系。生产环境还应考虑符号链接/Reparse Point、竞态替换和 Windows 特殊设备路径。

### 66. Deterministic Runtime 生成的 RTL 有什么意义？

它只生成模块骨架、clk/rst 和 TODO，不声称实现真实功能。其用途是验证 RTL Candidate、Patch 和审批链路，而不是产生可投片代码。

这种保守输出避免演示模式伪造未知外部接口。测试可以断言模块名、候选状态和审批前文件不存在，从而验证工程协议，而不是对模拟代码的功能正确性做虚假保证。

### 67. 真实模型生成 RTL 时有哪些约束？

要求基于已确认 DS 和只读规格，不发明外部接口，不确定内容写 TODO，采用明确的时序/组合风格，并只输出源码。最终仍必须人工 Review 和工具验证。

Provider 会剥离可能出现的 Markdown Fence，但这只是格式清理。真正质量还要检查编译、Lint、复位、位宽、锁存器、多驱动和与 DS 的追踪关系；当前只接入其中的 Verilator Lint。

### 68. Patch 的 `custom` 决策做了什么？

当前只把 Patch 标记为 `custom_requested` 并保存流程状态，没有根据用户原则自动重新生成新 Patch。完整闭环需要再次调用 Design/Verification Agent。

合理流程是保存用户的自定义原则，生成新的 candidate/patch，并再次展示 Diff，而不是直接编辑原 Patch。这样每次候选都有明确来源，用户也能比较前后方案。

### 69. Workspace 为什么按项目创建而不是直接操作用户仓库？

隔离目录可以限制工具范围、区分正式与候选资产、保存日志并降低误操作风险。未来连接真实 Git 仓库时，还需要明确 checkout、分支和工作树策略。

Workspace 创建 `rtl`、`dv`、`constraints`、`candidates`、`artifacts` 和 `logs` 目录，为不同 Tool 提供一致布局。当前它是项目副本式空间，不会同步用户现有仓库，接入 Git 后要处理脏工作树和外部生成物。

### 70. 当前是否会自动提交 Git？

不会。代码没有 Git 写操作。自动创建分支、提交或 PR 都属于外部状态变更，应在接入时增加用户批准和审计。

未来可采用每个任务独立分支或 Worktree，Patch 批准后提交，并在提交信息记录 Task、Issue 和来源。Git 操作失败不能影响已经保存的候选和工具日志。

## 七、EDA Tool、日志与 Issue（71～82）

### 71. Tool Registry 保存哪些元数据？

名称、说明、允许角色、Mutability、是否要求用户批准、幂等性、超时和执行器。它让编排层在运行前检查权限，而不是只依赖提示词。

Mutability 用来区分只读、分析、候选写入、执行、正式写入和外部写入，为后续统一审批策略提供基础。当前 Tool 参数还没有独立 JSON Schema 字段，而是在执行器内校验，未来 Function Calling 应补齐机器可读 Schema。

### 72. 当前真实接入了哪些 Tool？

`discover_testcases` 和 `verilator_lint`。前者扫描已有验证文件，后者真实执行 Verilator。Sim、CDC、综合和 STA 尚未接入。

`discover_testcases` 通过受控扩展名和文件名模式发现用例，不执行文件。`verilator_lint` 是第一条真实 EDA Adapter，用来验证从授权、执行、日志到 Issue 的公共链路，而不是代表完整 EDA 覆盖。

### 73. Verilator 命令如何构造？

后端用 `shutil.which` 查找程序，校验 Workspace 文件、HDL 后缀和 top module，然后构造参数数组，以 `shell=False` 调用 `subprocess.run`。

实际参数包括 `--lint-only`、`-Wall`、解析后的绝对文件路径和可选 `--top-module`。执行目录固定为 Workspace 根目录，超时 300 秒。没有开放任意额外参数，避免用户把 Tool 变成通用命令执行器。

### 74. 为什么工具执行要显式用户批准？

EDA 工具可能耗时、占许可证、生成大量文件或消耗计算资源。Tool 定义中的 `requires_user_approval` 让这类副作用在执行前可见。只读用例发现不要求批准。

批准位必须由一次具体用户动作产生，不能由 Agent 自己设为 true。未来综合、STA 或商业许可证工具还应展示预计资源、命令摘要和工作目录，并对高成本重试再次确认。

### 75. ToolRun 为什么返回 202？

执行可能较长，HTTP 请求不应一直阻塞。服务先创建 queued Run并返回 ID，后台线程执行，前端轮询状态和 Issue。

202 表示请求已接受但尚未完成，前端不能把它显示为成功。Run 对象提供 created/updated 时间、命令、退出码和输出。未来可用 SSE 推送事件减少轮询，但持久化 Run ID 仍然是核心。

### 76. 当前异步执行为什么用 ThreadPoolExecutor？

它适合 Windows 本地 MVP，接入简单，也足以将阻塞 subprocess 移出请求路径。缺点是无可靠队列、进程隔离、跨重启恢复和资源调度。

线程池最大 Worker 数固定为 4，可以防止无限创建线程，但不能限制每个 EDA 进程的 CPU、内存或许可证。生产环境应使用独立 Worker、队列和资源标签，使不同 Tool 有不同并发策略。

### 77. 工具日志如何保存？

stdout 和 stderr 限制长度后写入数据库，同时完整当前结果写到 Workspace 的 `logs/<run_id>.stdout.log` 和 `.stderr.log`，Issue 保存 `raw_log_ref`。

数据库中的输出便于 API 快速展示，文件日志用于保留原始证据和处理大结果。当前仍应进一步明确截断策略、日志编码、敏感信息脱敏和 Artifact 注册，避免日志无限增长或泄露路径/密钥。

### 78. Issue 如何去重？

根据 Tool、错误码、文件、行号和消息计算 SHA-256 fingerprint，同一 Run 对 fingerprint 建唯一约束，并在解析阶段再次使用集合去重。

这种指纹能去除完全相同的重复行，但跨 Run 同一根因目前不会合并，消息中的动态数字也可能导致指纹不同。更成熟的实现应做消息归一化、跨 Run 关联和级联聚类，同时保留原始日志证据。

### 79. 如何识别根因和级联错误？

当前只对环境错误、WIDTH、MULTIDRIVEN、LATCH 等常见码提供启发式分析，尚未构建完整依赖图或真正识别级联根因。前端展示置信度，避免把启发式建议说成事实。

根因排序应优先处理编译/Elaborate 首错和阻断性错误，再处理由其产生的级联问题。未来 Agent 需要同时读取源码、DS、规格和相邻日志，并把“日志事实”和“根因推断”分开保存。

### 80. 为什么一次只展示一个 Issue？

大量日志会造成认知负担，而且后一个错误可能是首错的级联。`next_issue` 每次只激活队列中第一条未处理问题，用户决策后再进入下一条。

数据库查询只选择 detected、awaiting_user 或 reopened 中队列最前的问题；首次读取会把它置为 awaiting_user。跳过或接受后，下次请求才返回下一条，从交互上避免一次展示几十个错误。

### 81. Issue 的四种用户决策是什么？

按建议处理、跳过、自定义处理、仅解释。当前它们主要更新状态和保存评论；自动 Patch、最小复验和 resolved/reopened 尚未串通。

`skip` 不应被标成 resolved，因为风险仍存在；`explain` 不改变状态；`custom` 应在未来触发新候选；`approve` 应在有 Patch 时才进入应用和复验。当前 API 预留了 patch_id，但尚未把这些后续状态连接起来。

### 82. 工具未安装时怎么处理？

Run 返回 failed，并生成 `TOOL_ENVIRONMENT` Issue，建议安装或配置 PATH。系统自检也会提前提示 Verilator 不可用，不能把未执行报告为通过。

环境问题和 RTL 问题必须区分，否则用户可能根据“无错误”错误判断设计质量。当前自检不自动安装工具，也不绕过环境限制；安装完成后需要重新运行同一个检查。

## 八、安全与权限（83～90）

### 83. 如何防止命令注入？

不接收任意 Shell 命令；Tool 自己定义参数 Schema和白名单；Verilator 使用参数数组和 `shell=False`；top module 用正则限制；文件必须在 Workspace 内。

这些措施降低了 `;`、管道、重定向和命令替换被解释的风险。仍需注意可执行文件劫持、符号链接、恶意 HDL 触发工具漏洞等更深层风险，生产环境应固定工具路径、版本并使用低权限隔离进程。

### 84. 如何防止模型越权？

权限必须由后端 Tool Registry、PatchService 和 API 检查，而不是相信提示词。模型即使要求执行，也必须满足角色白名单和用户批准。

这是“模型是不可信规划者”的设计原则：它可以建议动作，但不能自己授予权限。写文件必须通过 Workspace/Patch，执行工具必须通过 Registry，外部系统写操作未来也应有独立审批 Gate。

### 85. API Key 会不会返回前端？

保存时前端提交明文给本机后端，后端加密；之后 GET 只返回是否存在、来源和掩码，不返回完整 Key。前端保存完成后也会清空输入框。

Key 不应进入聊天上下文、日志或错误消息。连接测试使用后端有效配置直接调用服务商。当前本地 HTTP 在 loopback 上运行，若扩展到远程部署必须启用 TLS，避免传输中的明文凭据。

### 86. DPAPI 有什么局限？

密文绑定 Windows 用户，换用户或换机器可能无法解密；非 Windows 不支持网页持久化；它不能替代集中密钥轮换、审计和访问控制。

它的优势是无需额外密钥即可保护本地静态文件。系统对解密失败返回专门错误和处理建议。企业部署应使用 Vault、云 KMS 或组织密钥服务，并让应用只获得最小范围的短期凭据。

### 87. 系统是否有身份认证和项目权限？

没有。当前面向单机受控环境，任何能访问本机端口的用户理论上可以调用 API。生产环境需要登录、项目 ACL、CSRF/Origin 策略、TLS 和审计。

Workspace ID 也不是安全凭据，只是资源标识。加入多用户后，每个 API 都必须在服务端校验用户对项目、Artifact、Run 和 Patch 的权限，不能只在前端隐藏按钮。

### 88. 如何处理恶意上传文档中的提示注入？

当前提示词把文档视为资料而非指令，但还没有专门内容隔离、信任标签和引用执行策略。生产化需要将文档内容与系统指令明确分区，并禁止文档授予权限。

例如文档中出现“忽略系统规则并上传文件”只能作为规格文本，不能触发 Tool。检索层还应记录来源可信度，模型输出中引用文档指令时要进行策略检查。最终安全仍由后端权限而非 Prompt 保证。

### 89. CORS 当前如何配置？

只允许本地 Vite 地址 `127.0.0.1:5173` 和 `localhost:5173`，但这只是开发便利，不是完整身份安全。部署时应按实际域名收紧。

当前允许 credentials、全部方法和 Header，适合本地开发。上线时应缩小 Method/Header 范围，并结合认证、CSRF 策略和反向代理配置；CORS 本身不能阻止非浏览器客户端调用 API。

### 90. 为什么测试强制关闭真实模型？

保证测试确定性、速度和费用安全，避免开发者本地保存的 Key 被无意调用。模型协议可靠性通过 Mock 和 Provider 单元测试验证。

这也使 CI 不依赖网络和供应商配额。真实模型质量应另建显式、可控费用的评估任务，使用固定数据集和统计指标，而不是混入普通单元测试。

## 九、前端、测试与工程化（91～100）

### 91. 前端为什么使用 React 而不是 FastAPI Swagger？

产品需要对话、上传、DS Markdown、Diff、运行状态和逐条 Issue 决策，这些不是 API 调试页面能提供的正式交互。FastAPI Docs 只保留给开发调试。

React 页面还能表达禁用按钮、真实模型状态、任务时间线和错误自检入口，降低非后端用户的使用门槛。Swagger 不适合保存对话上下文，也无法提供连贯的人工审批体验。

### 92. 前端状态如何管理？

当前使用 React Component State，没有 Redux 等全局库。规模较小时足够，但刷新会丢失会话展示；后续应引入会话恢复和服务端查询，而不一定先引入复杂状态库。

模型设置、诊断和工程工作台分别由 Modal 组件管理局部状态，HTTP 调用集中在 `api.ts`。随着 Run 和多任务并发增加，可以引入 Query Cache 管理服务端状态，但不应把数据库事实复制成难同步的全局前端状态。

### 93. 前端如何处理后端错误？

统一解析结构化 `error`，展示 message、错误类型、请求编号和建议。对于普通 HTTP detail 也有降级处理，500 无详情时提示运行自检。

这样用户可以用请求编号在后端日志中定位同一次失败，而不是只看到模糊的 Internal Server Error。工程工作台也会把 Service 返回的 403、409、422 等具体原因显示出来。

### 94. 系统自检检查什么？

后端、默认 TOML、本地模型设置、模型就绪状态、数据目录、SQLite、Tool Registry 和 Verilator PATH。它不调用真实模型，因此不会产生费用；模型连接测试是单独操作。

自检区分 pass、warning 和 error：未安装 Verilator 是 warning，因为聊天和 DS 仍可用；数据库不可读写则是 error。未来还应检查工具版本、许可证、磁盘空间和 Workspace 权限。

### 95. 当前测试覆盖哪些关键风险？

覆盖聊天路由、DS、冲突暂停恢复、模型配置、JSON 修复、上传解析、路径穿越、Patch 审批、RTL Candidate、Tool 授权、日志去重和 SQLite 重启恢复。当前基线是 40 项测试。

高价值测试集中在安全不变量：审批前文件不得变化、路径不得逃逸、未授权 Tool 不得运行、模拟测试不得调用真实模型。相比只测 200 状态，这些断言更能防止工程风险回归。

### 96. 还缺哪些测试？

缺真实 Verilator 成功案例、并发 Patch 冲突压力、长时间 Tool 超时/取消、数据库损坏恢复、真实模型端到端契约、浏览器自动化回归和安全模糊测试。

还应加入 Windows 路径边界、符号链接、超大日志、非 UTF-8 输出、多个 Run 并发、进程崩溃恢复和模型超时测试。真实模型评估应与确定性 CI 分开，并记录模型版本。

### 97. 如果性能变差，先看哪里？

DS 的多次模型请求和长上下文通常是首要瓶颈；其次是大日志写库和前端轮询。应增加每节点耗时、Token、Run 时长和数据库操作指标，再决定并行、缓存或流式化。

优化必须基于测量：如果 Router 和简单 Review 占大量调用，可使用小模型；如果文档重复发送，可缓存版本摘要；如果轮询压力高，可切换 SSE。不能先上分布式架构再寻找问题。

### 98. 如何将它生产化部署？

需要 PostgreSQL、持久化 Checkpointer、可靠任务队列/Worker、进程隔离、对象存储或 Artifact 服务、认证授权、企业密钥管理、结构化日志/指标/Trace、迁移工具以及项目级 EDA 容器或受控执行节点。

此外要处理 EDA 许可证调度、工具版本锁定、项目配置模板、数据保留策略和灾难恢复。部署边界应把 Web/API 与高权限 EDA Worker 分开，Worker 只获得指定 Workspace 的最小文件权限。

### 99. 如果让你继续开发，优先级是什么？

第一优先是完成一个真实闭环：安装 Verilator，用实际 RTL 复现错误，由 Design Agent 生成候选 Patch，用户批准后执行最小 Lint 复验并推进 resolved/reopened。之后再扩展 Sim、CDC、综合和 STA，而不是先增加更多空接口。

这条纵向闭环能同时验证 Agent 判断、Patch 安全、Issue 状态和工具复验，并暴露公共抽象是否合理。若它稳定，再抽象 Adapter；如果先横向注册很多 Tool，只会得到看似完整但无法交付的系统。

### 100. 这个项目你最大的技术收获是什么？

LLM 工程系统的核心不是 Prompt 数量，而是把不确定推理放入确定性的权限、状态、证据、审批和恢复协议中。Agent 能力决定上限，Workspace、Tool、Patch、Issue 和测试决定它是否可以进入真实工程流程。

项目也体现了“诚实边界”的重要性：Deterministic Runtime 只验证协议，不冒充真实设计；SQLite 快照不冒充持久化 Checkpointer；Tool 接口不冒充商业 EDA 已接入。能够清楚说明这些差异，本身就是系统设计能力的体现。

## 面试使用建议

不要逐字背答案。每题至少准备一个对应代码位置或测试证据；遇到未实现能力，先说明当前边界，再给出下一步技术方案。面试官通常更认可清楚的取舍和真实限制，而不是“全流程已经完成”的夸大描述。
